# From-source Python packages (numpy, h5py, ...) — design & rollout plan

> **Status (2026-08-21): implemented — kept as a design record.**
>
> The plan below shipped. `numpy-cp311..cp313t` and `h5py-cp311..cp313` build
> from source (`source.type: tarball`), the per-interpreter build-backend
> columns (`cython-cp3XX`, `meson-python-cp3XX`, …) exist, and
> `tools/gen_python_recipes.py` has since generalized the approach: the sdist
> path is now the **default** for generated packages too. Current behaviour is
> documented in [python-wheels.md](../python-wheels.md).
>
> One item is obsolete: **C8's "windows = loud `build.ps1` stub (exit 1)"**.
> `recipes/numpy-cp311` now has a real windows matrix entry — its `build.ps1`
> is a full meson-python/MSVC from-source build against cvcpkg's OpenBLAS,
> with an in-build gemm + no-vendored-libs verification. h5py's windows
> `build.ps1` remains the loud stub described below.
>
> The in-tree recipes have also diverged from the verbatim drafts in §3/§4
> (revision bumps; numpy's macOS column now links cvcpkg's own OpenBLAS
> instead of Accelerate, reversing C6). Where this document and
> `recipes/*/recipe.yaml` disagree, the recipes are authoritative.

_Generated by the design workflow; empirically grounded (numpy+h5py from-source builds proven to link cvcpkg openblas/hdf5, no vendored libs, proper dist-info)._

I have the mechanics confirmed. Two facts decide the reconciliation:

1. `cvc_python_exe` (python-wheel.sh:32-51) resolves the interpreter **only** from `CVC_DEPS_PREFIX`, and that interpreter imports only from **its own** `CVC_DEPS_PREFIX/lib/pythonX.Y/site-packages`. Build backends declared as `depends.build` land in `CVC_BUILD_PREFIX` → **not importable unless `PYTHONPATH` bridges them.** The h5py-finding build.sh omits this bridge; the numpy-finding build.sh has it. This is the single most important fix.
2. The per-file `realpath --relative-to` patchelf idiom (build-python.sh:146-150) is the established repo pattern, and its comment confirms cvcpkg's own relocation pass **prepends `$ORIGIN` and preserves `$ORIGIN`-relative entries** — so recipe-set rpath + cvcpkg pass are complementary, not conflicting.

Everything below is reconciled against these.

# 1. CONFLICT CHECK (resolved)

**C1 — Build-backend provisioning: wheelhouse+activation (build-tools finding, Option A) vs discrete per-interpreter recipes (numpy/h5py/BSD findings).**
RESOLVE → **discrete per-interpreter `python_wheel` recipes** (`cython-cp3XX`, `meson-python-cp3XX`, `pkgconfig-cp3XX`, `wheel-cp3XX`, plus meson-python's pure-python deps `packaging-cp3XX`, `pyproject-metadata-cp3XX`), generated by the existing `tools/gen_python_recipes.py`, declared with real `depends` edges. Reasons: (a) transitive closure (meson-python→packaging→pyproject-metadata) is resolved by cvcpkg's own dependency graph instead of a parallel `wheelhouse.lock` + activation helper + a possible core schema change; (b) reuses the exact machinery that already emits `numpy-cp311/312/313`; (c) the build-tools finding's only real objection to discrete recipes — "they ship to users" — **does not apply**: declared as `depends.build` they land in `CVC_BUILD_PREFIX` and are stripped from the numpy/h5py deliverable. The "from-source" mandate is explicitly about the **deliverables** (numpy/h5py that link our libs); build backends are noarch host scaffolding where a `py3-none-any` wheel is valid on every platform incl. the BSDs, so `python_wheel` is correct for them.

**C2 — "Only source fetch touches network" vs `--no-build-isolation` needing backends.**
No real conflict. Builder finding proved the build step is **not** sandboxed — offline is a *contract*, not enforced. RESOLVE → every `pip` call carries `--no-build-isolation --no-index --no-deps`; backends come from `CVC_BUILD_PREFIX` via `PYTHONPATH`. **Both finding build.sh drafts are missing `--no-index` on the `pip wheel` step — added in the final versions.**

**C3 — rpath ownership: recipe patchelf vs cvcpkg's post-build patchelf pass.**
Complementary. cvcpkg's pass walks `install_dir/lib/**/*.so*`, keeps `$ORIGIN`-relative entries, drops absolutes, prepends bare `$ORIGIN`, **runs only when `CVC_LINK==shared`, and excludes OpenBSD.** RESOLVE → recipe sets a per-file `$ORIGIN`-relative RUNPATH (survives the pass); do **not** leave an absolute build-prefix rpath (gets stripped → broken load). **OpenBSD caveat the findings under-flagged:** OpenBSD's ld.so ignores `$ORIGIN` *and* cvcpkg skips its patchelf pass there, so the ext resolves libhdf5/openblas only via cvcpkg's runtime activation (`LD_LIBRARY_PATH` from the merged prefix), not rpath. Set the rpath anyway (harmless), but OpenBSD correctness depends on the activation env — a test gate (§5).

**C4 — rpath depth: hardcoded (numpy `../../../..`, h5py `../../..`) vs per-file.**
RESOLVE → **per-file `realpath --relative-to`** (build-python.sh idiom) in both recipes. numpy ships ext at depth-1 (`numpy/*.so`) and depth-2 (`numpy/_core/*.so`, `numpy/linalg/*.so`); per-file computation is correct for both automatically and can never be hardcoded wrong.

**C5 — openblas pkg-config module name.** numpy finding verified it is `openblas` (not `scipy-openblas`). RESOLVE → `-Dblas=openblas -Dlapack=openblas`; set `PKG_CONFIG_LIBDIR` to *only* our prefix so no stray/system `.pc` (or a future `scipy-openblas.pc` implying ILP64) leaks in; `allow-noblas=false` to fail loud.

**C6 — macOS BLAS.** openblas recipe has no macOS build (Accelerate). RESOLVE → numpy on macOS uses `-Dblas=accelerate`; `MACOSX_DEPLOYMENT_TARGET=13.3` (Accelerate new-LAPACK floor, up from the base 13.0). No prefix-lib rpath needed there.

**C7 — `build_type_independent`: numpy finding `true` vs h5py finding "NOT independent".**
RESOLVE → **`true` for both.** Python ABI is stable across cvcpkg build types; nobody consumes a debug-built numpy/h5py, and a debug consumer linking a release ext is fine. Build once, release-optimized (`-O2` via matrix env), halving builder load. h5py's build-type-dependent stance is dropped.

**C8 — Windows: numpy finding writes a from-source `build.ps1` vs BSD finding "defer, keep prebuilt wheel."**
Structural constraint the findings missed: **`source.type` is recipe-wide** — a recipe is *either* `python_wheel` *or* `tarball`, so a single converted recipe cannot keep a prebuilt-wheel windows column. RESOLVE → convert numpy/h5py to `tarball`; **windows = loud `build.ps1` stub (exit 1)** in both; enable-now matrix = linux + freebsd + netbsd + openbsd + macos. This **regresses windows numpy** (today served by prebuilt wheel) until the windows-from-source port lands — flagged as the top decision in §5. numpy-windows-from-source is feasible fast-follow (`Invoke-CvcMesonBuild` exists, openblas builds on windows, DLL discovery via `os.add_dll_directory`); h5py-windows stays stubbed longer (no PE rpath).

**C9 — HDF5 version pin.** h5py build.sh hardcodes `HDF5_VERSION=1.14.4` / asserts `1.14.`/`.310`; recipe depends `hdf5 ^1.14`. RESOLVE → keep, and bump all three in lockstep with the `hdf5` recipe (§5 drift note).

**C10 — wasm/wasi/cosmo.** All findings agree: static interpreter, no extension-module ABI, no BLAS → **excluded**, not stubbed (no matrix entry).

# 2. SEQUENCED IMPLEMENTATION PLAN

Enable-now platform matrix (both deliverables): **linux, freebsd, netbsd, openbsd, macos.** Defer: windows (stub). Exclude: wasm/wasi/cosmo.

**Step 0 — Native tool deps already exist:** `meson`, `ninja`, `pkg-config` (native recipes, on PATH in build closure). No action.

**Step 1 — Build-backend recipes (BLOCKS everything).** Generate per-interpreter (cp311 first; cp312/cp313/cp313t replicate) `python_wheel` recipes via `tools/gen_python_recipes.py`:
- `cython-cp3XX`
- `meson-python-cp3XX` → `depends.runtime: packaging-cp3XX, pyproject-metadata-cp3XX` (also generate those two)
- `pkgconfig-cp3XX` (the Python `pkgconfig` module — h5py backend import)
- `wheel-cp3XX`
Each: `source.type: python_wheel` (noarch `py3-none-any`), `python:{interpreter: python3XX, abi: cp3XX}`, `depends.build/runtime: python3XX`, `build.sh` = `. ../_common/python-wheel.sh; cvc_pip_install_wheel`.
VERIFY per recipe: `cvcpkg validate`; build cp311 set; confirm each lands at `…/lib/python3.11/site-packages/<mod>`; `cvc_python_check "import cython, mesonpy, pkgconfig, wheel, packaging, pyproject_metadata"`.

**Step 2 — Convert `numpy-cp311` to from-source** (recipe.yaml + build.sh below). numpy before h5py — h5py build-imports numpy's C API.
VERIFY: `cvcpkg validate numpy-cp311`; build on linux; `readelf -d …/numpy/_core/_multiarray_umath*.so | grep -E 'NEEDED.*openblas|RUNPATH'` shows `NEEDED libopenblas.so.0` + `$ORIGIN`-relative RUNPATH; assert **no** `numpy/*.libs/` dir; `np.show_config()` reports our openblas; `(a@a.T)` gemm works.

**Step 3 — Convert `h5py-cp311` to from-source** (files below; the finding's drafts + the PYTHONPATH bridge + `--no-index`).
VERIFY: build on linux; `readelf -d …/h5py/*.so | grep NEEDED` shows `libhdf5.so.310` (unmangled); no `h5py.libs/`; round-trip write/read; `h5py.version.hdf5_version` starts `1.14.`.

**Step 4 — BSD bring-up** (freebsd, netbsd, openbsd). Same build.sh. NetBSD: ensure cvcpkg ninja wins on PATH (pkgsrc ninja crashes under empty env — env-netbsd note). OpenBSD: verify runtime lib resolution via activation env (C3 caveat), not rpath.
VERIFY: build both recipes each BSD; round-trip + NEEDED-soname checks.

**Step 5 — macOS.** numpy `-Dblas=accelerate` (skip prefix rpath); h5py `install_name_tool` `@loader_path` relocation. `MACOSX_DEPLOYMENT_TARGET=13.3` for numpy.
VERIFY: `otool -L` on exts shows `@rpath/...`; round-trip.

**Step 6 — Replicate the trios** for cp312, cp313, then cp313t (free-threaded: `cvc_python_check` also asserts GIL stays disabled).

**Step 7 — Windows follow-up (separate task):** numpy-from-source `build.ps1` (MSVC meson + openblas + `os.add_dll_directory`), then h5py. Until then windows stub stands.

# 3. FINAL `recipes/h5py-cp311/` (verbatim, reconciled)

### `recipes/h5py-cp311/build.sh`
```bash
#!/usr/bin/env bash
# recipes/h5py-cp311/build.sh — build h5py 3.16.0 FROM SOURCE against cvcpkg's
# OWN HDF5 (recipes/hdf5, libhdf5.so.310) for the cp311 interpreter column.
#
# WHY FROM SOURCE: the PyPI wheel bundles an auditwheel-mangled libhdf5 in
# h5py.libs/ and ships nothing for the BSDs. We compile the Cython extensions so
# the .so link cvcpkg's UNMANGLED libhdf5.so.310 by soname and resolve it out of
# the SAME activated prefix — no vendored copy, no soname collision.
#
# PROVEN MECHANIC: HDF5_DIR=<prefix> pip wheel <sdist> yields a wheel whose ext
# .so carry NEEDED libhdf5.so.310. We pip-install that wheel into this recipe's
# staging prefix (real dist-info/RECORD/METADATA, pip-resolvable later), then
# stamp each .so with an $ORIGIN-relative RUNPATH to <prefix>/lib.
set -euo pipefail

SCRIPT_DIR="$(cd "$(dirname "$0")" && pwd)"
# shellcheck disable=SC1090
source "${SCRIPT_DIR}/../_common/env-${CVC_PLATFORM}.sh"
# shellcheck disable=SC1091
source "${SCRIPT_DIR}/../_common/python-wheel.sh"   # cvc_python_exe

# ── 1. Prefix interpreter for this ABI ──────────────────────────────────────
: "${CVC_PYTHON_ABI:=cp311}"
PY_EXE="$(cvc_python_exe)"                 # <CVC_DEPS_PREFIX>/bin/python3.11
echo "h5py-cp311: building against ${PY_EXE}"

# ── 1b. Bridge BUILD-only backends into the DEPS-prefix interpreter ──────────
# cvc_python_exe runs the interpreter from CVC_DEPS_PREFIX, which imports only
# its OWN site-packages. Cython / pkgconfig / wheel are depends.build → they live
# in CVC_BUILD_PREFIX's site-packages, so --no-build-isolation cannot import them
# without this bridge. (numpy is a runtime dep → already in CVC_DEPS_PREFIX.)
_D="${CVC_PYTHON_ABI#cp}"; _D="${_D%t}"
_PYMM="${_D:0:1}.${_D:1}"                   # cp311 -> 3.11
if [ -n "${CVC_BUILD_PREFIX:-}" ]; then
  export PYTHONPATH="${CVC_BUILD_PREFIX}/lib/python${_PYMM}/site-packages${PYTHONPATH:+:${PYTHONPATH}}"
fi

# ── 2. Point h5py's build at OUR HDF5 ───────────────────────────────────────
: "${CVC_DEPS_PREFIX:?CVC_DEPS_PREFIX must be set}"
export HDF5_DIR="${CVC_DEPS_PREFIX}"
# Pin explicitly so h5py does NOT compile+RUN a probe binary (fails on cross/BSD
# runners). MUST track recipes/hdf5 upstream_version.
export HDF5_VERSION="1.14.4"
export HDF5_MPI="OFF"                       # serial HDF5, never MPI

echo "h5py-cp311: HDF5_DIR=${HDF5_DIR}  HDF5_VERSION=${HDF5_VERSION}"
[ -e "${HDF5_DIR}/include/hdf5.h" ] || {
    echo "h5py-cp311: ${HDF5_DIR}/include/hdf5.h missing — is hdf5 in the closure?" >&2
    exit 1; }

# ── 3. Build the wheel from the sdist (offline, no isolation) ───────────────
WHEELHOUSE="${CVC_BUILD_DIR}/wheelhouse"
mkdir -p "${WHEELHOUSE}"
"${PY_EXE}" -m pip wheel \
    --no-deps --no-build-isolation --no-index --no-cache-dir \
    --wheel-dir "${WHEELHOUSE}" \
    "${CVC_SOURCE_DIR}"

WHEEL="$(find "${WHEELHOUSE}" -maxdepth 1 -name 'h5py-*.whl' -print -quit)"
[ -n "${WHEEL}" ] || { echo "h5py-cp311: no wheel produced" >&2; exit 1; }
echo "h5py-cp311: built $(basename "${WHEEL}")"

# ── 4. Install ONLY site-packages into the (empty) staging prefix ───────────
"${PY_EXE}" -m pip install \
    --no-index --no-deps --no-compile \
    --prefix "${CVC_INSTALL_DIR}" \
    "${WHEEL}"

H5PY_DIR="$(find "${CVC_INSTALL_DIR}" -maxdepth 4 -type d -name h5py -print -quit)"
[ -n "${H5PY_DIR}" ] || { echo "h5py-cp311: staged h5py/ not found" >&2; exit 1; }
SITE_PACKAGES="$(dirname "${H5PY_DIR}")"
echo "h5py-cp311: staged into ${SITE_PACKAGES}"

# ── 5. Relocatable RUNPATH on the extension .so (per-file depth) ────────────
if [[ "${CVC_PLATFORM}" == "macos" ]]; then
    command -v install_name_tool >/dev/null 2>&1 || {
        echo "h5py-cp311: install_name_tool required on macOS" >&2; exit 1; }
    while IFS= read -r -d '' _so; do
        _rel="$(python3 -c 'import os,sys;print(os.path.relpath(sys.argv[2],os.path.dirname(sys.argv[1])))' "$_so" "${CVC_INSTALL_DIR}/lib" 2>/dev/null || echo ../../..)"
        chmod u+w "${_so}" 2>/dev/null || true
        while IFS= read -r dep; do
            case "${dep}" in
                "${CVC_DEPS_PREFIX}"/*|"${CVC_BUILD_PREFIX:-/nonexistent}"/*)
                    install_name_tool -change "${dep}" "@rpath/$(basename "${dep}")" "${_so}" 2>/dev/null || true ;;
            esac
        done < <(otool -L "${_so}" | awk 'NR>1 {print $1}')
        install_name_tool -add_rpath "@loader_path/${_rel}" "${_so}" 2>/dev/null || true
        install_name_tool -add_rpath "@loader_path"         "${_so}" 2>/dev/null || true
    done < <(find "${H5PY_DIR}" -name '*.so' -print0)
else
    # ELF (Linux/BSD): $ORIGIN-relative RUNPATH so cvcpkg's patchelf pass (which
    # prepends bare $ORIGIN and preserves $ORIGIN entries) keeps it. patchelf is a
    # REQUIRED host tool here. NOTE: OpenBSD ld.so ignores $ORIGIN and cvcpkg skips
    # its pass there — OpenBSD resolves libhdf5 via cvcpkg runtime activation env.
    command -v patchelf >/dev/null 2>&1 || {
        echo "h5py-cp311: patchelf required on ${CVC_PLATFORM}" >&2; exit 1; }
    while IFS= read -r -d '' _so; do
        _rel="$(realpath --relative-to="$(dirname "${_so}")" "${CVC_INSTALL_DIR}/lib")"
        patchelf --set-rpath "\$ORIGIN:\$ORIGIN/${_rel}" "${_so}"
    done < <(find "${H5PY_DIR}" -name '*.so' -print0)
fi

command -v cvc_rewrite_install_paths >/dev/null 2>&1 && cvc_rewrite_install_paths || true

# ── 6. Real round-trip verification (proves it linked OUR libhdf5) ──────────
export PYTHONPATH="${SITE_PACKAGES}${PYTHONPATH:+:${PYTHONPATH}}"
_LOADPATH="${CVC_DEPS_PREFIX}/lib${CVC_BUILD_PREFIX:+:${CVC_BUILD_PREFIX}/lib}"
if [[ "${CVC_PLATFORM}" == "macos" ]]; then
    export DYLD_LIBRARY_PATH="${_LOADPATH}${DYLD_LIBRARY_PATH:+:${DYLD_LIBRARY_PATH}}"
else
    export LD_LIBRARY_PATH="${_LOADPATH}${LD_LIBRARY_PATH:+:${LD_LIBRARY_PATH}}"
fi

"${PY_EXE}" - <<'PYCHECK'
import os, tempfile, numpy as np, h5py
exp = np.arange(24, dtype="f8").reshape(4, 6)
with tempfile.TemporaryDirectory() as d:
    p = os.path.join(d, "rt.h5")
    with h5py.File(p, "w") as f:
        f.create_dataset("cube", data=exp); f.attrs["stamp"] = "cvcpkg"
    with h5py.File(p, "r") as f:
        got = f["cube"][()]; assert f.attrs["stamp"] == "cvcpkg"
assert np.array_equal(got, exp), "round-trip mismatch"
linked = h5py.version.hdf5_version
print("h5py", h5py.__version__, "-> HDF5", linked, "numpy", np.__version__)
assert linked.startswith("1.14."), f"linked HDF5 {linked} is not the cvcpkg build"
print("h5py-cp311 round-trip OK")
PYCHECK
echo "h5py-cp311: build + verification complete"
```

# 4. `recipes/numpy-cp311/` (verbatim draft, reconciled)

### `recipes/numpy-cp311/build.sh`
```bash
#!/usr/bin/env bash
# recipes/numpy-cp311/build.sh — build NumPy 2.4.6 FROM SOURCE (meson-python)
# against cvcpkg's OpenBLAS (LP64), then install the resulting wheel into the
# python311 interpreter's site-packages. No numpy.libs/ — the ext links our
# libopenblas.so.0 by soname, resolved via an $ORIGIN-relative RUNPATH.
set -euo pipefail
SCRIPT_DIR="$(cd "$(dirname "$0")" && pwd)"
source "${SCRIPT_DIR}/../_common/env-${CVC_PLATFORM}.sh"      # sets CVC_JOBS, toolchain
source "${SCRIPT_DIR}/../_common/python-wheel.sh"             # cvc_python_exe

: "${CVC_PYTHON_ABI:=cp311}"
PY="$(cvc_python_exe)"                        # <CVC_DEPS_PREFIX>/bin/python3.11
DEPS="${CVC_DEPS_PREFIX:-${CVC_INSTALL_DIR}}"
BLD="${CVC_BUILD_PREFIX:-${DEPS}}"
_D="${CVC_PYTHON_ABI#cp}"; _D="${_D%t}"; _PYMM="${_D:0:1}.${_D:1}"

# Bridge BUILD-only backends (meson-python, Cython, packaging, pyproject-metadata)
# from CVC_BUILD_PREFIX into the DEPS-prefix interpreter, and put the meson/ninja/
# pkg-config CLIs (native recipes, in build prefix) first on PATH.
export PATH="${BLD}/bin:${DEPS}/bin:${PATH}"
export PYTHONPATH="${BLD}/lib/python${_PYMM}/site-packages${PYTHONPATH:+:${PYTHONPATH}}"
export MESON="${BLD}/bin/meson"
export NINJA="${BLD}/bin/ninja"

# ── BLAS selection ──────────────────────────────────────────────────────────
BLAS_ARGS=()
case "${CVC_PLATFORM}" in
  macos)
    BLAS_ARGS+=( -C setup-args=-Dblas=accelerate -C setup-args=-Dlapack=accelerate ) ;;
  *)
    # Hermetic pkg-config: ONLY our prefix's openblas.pc visible (module name is
    # `openblas`, LP64, no symbol suffix). LIBDIR *replaces* the system search.
    export PKG_CONFIG="${BLD}/bin/pkg-config"
    export PKG_CONFIG_PATH="${DEPS}/lib/pkgconfig"
    export PKG_CONFIG_LIBDIR="${DEPS}/lib/pkgconfig"
    BLAS_ARGS+=(
      -C setup-args=-Dblas=openblas
      -C setup-args=-Dlapack=openblas
      -C setup-args=-Dallow-noblas=false      # fail loud if openblas not found
      -C setup-args=-Duse-ilp64=false ) ;;    # our openblas is LP64
esac

WHEELOUT="${CVC_BUILD_DIR}/wheelhouse"; mkdir -p "${WHEELOUT}"

# ── Build from source (offline, no isolation) ───────────────────────────────
"${PY}" -m pip wheel \
  --no-build-isolation --no-deps --no-index \
  --wheel-dir "${WHEELOUT}" \
  "${BLAS_ARGS[@]}" \
  -C builddir="${CVC_BUILD_DIR}/meson" \
  -C compile-args=-j"${CVC_JOBS}" \
  "${CVC_SOURCE_DIR}"

WHEEL="$(find "${WHEELOUT}" -maxdepth 1 -name 'numpy-*.whl' -print -quit)"
```
